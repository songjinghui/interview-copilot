## R1 · P1 · 冷却期闸门未明确区分现有限制与本次投递的未来影响

**证据：** 架构 §5.2（L149–155）只给出 `limits.evaluate()` 的三态及分支；§3 虽列出“影响预览”，未定义预览结果如何决定闸门。VISION §4.4（L292、L300–311）明确：当前仍在冷却期，以及本次投递将触发已知冷却期，都应暂停；待核实时，本岗位为重点或影响其他重点机会都需确认。

**触发场景：** 当前没有冻结，但投递练手岗位将触发公司级限制、占用重点岗位窗口。若三态只判断“现在是否受限”，就会返回无限制，跳过第二次确认。另一个独立场景是本岗位本身为重点、没有其他重点机会，规则却待核实；现有“影响重点机会”表述未把这一分支写明。

**修订要求：** 为规则评估定义输入和结果，区分当前投递资格、本次动作将触发的影响、受影响机会、依据与未知项、是否需要第二次确认及原因。列出完整决策表，保留最多两次确认及三种用户选择。用户确认不改变平台实际限制。

**复审验收：** 当前受限、未来才触发限制、待核实且本岗重点、练手影响重点、待核实且无重点关联，五组场景都有明确分支；批量清单中前一项提交改变后续限制时有重新评估规则。

## R2 · P1 · 投递缺少可恢复、不会盲目重复执行的协议

**证据：** 架构 §4.2（L114）只有申请事件追加，§5.2（L149–158）只有“机会 + 材料版本”的授权及执行结果分类。未定义投递尝试身份、执行前持久化、重复命令处理、授权撤回或结果不明后的恢复路径。VISION §3.4–3.5（L98–110）要求确认投递渠道，且超时后先核验、不直接重复投递。

**触发场景：** 招聘渠道已经收件，程序在保存回执前退出。重启后如果只重跑原任务，会再次投递；只记录“结果不明”也没有回答如何安全恢复。同一机会切换渠道时，仅校验机会与材料版本还可能复用原渠道的授权。

**修订要求：** 定义一次投递意图、对应授权及执行尝试之间的关系。授权至少绑定明确渠道/账号、选中岗位与材料；发送前持久化尝试，重复命令复用该尝试；结果不明先查回执，无法核实则等待人工处理。发送前检查授权仍有效，选择手动投递后不能同时执行自动提交。明确哪些读取能重试、哪些对外动作不能直接重试。

**复审验收：** 连点提交、发送后崩溃、超时、重启、撤回授权、切换渠道、选择手动后旧任务恢复，均有状态转移及副作用边界。无需引入分布式队列，但需写清本地事务与恢复责任。

## R3 · P1 · 复盘的“当时证据”尚无明确的版本引用关系

**证据：** 架构 §4.2（L110–119）写“同一机会引用的版本号固定”，但未定义申请、面试、JD 版本、材料版本、转写修订与报告之间的关系；§5.3（L167）直接以 JD、材料、转写为输入。VISION §3.9、§5.3 要求使用当时的 JD 和提交材料，结论可回到原话，转写修改后提示相关分析更新。

**触发场景：** 投递时使用 JD A 与简历 V1，面试前岗位改成 JD B、用户改成简历 V2；若报告从“当前岗位/当前材料”读取，就会评价错误的申请背景。转写纠正说话人后，旧报告的引用也可能指向被覆盖的文本。一个机会有多次申请或补材料时，只在机会层固定一个材料版本不足以表示历史。

**修订要求：** 增加实体关系与版本引用约定：申请保存当次 JD 与材料引用；面试明确关联申请或补录背景；报告运行固定输入版本；引用关联转写版本、片段/时间点；输入校正使旧报告标记过时，重算形成新报告版本。支持尚无投递记录就直接补录面试，不为了外键制造虚假申请。

**复审验收：** 后续抓取、更换简历、转写修订不改变历史报告所指证据；旧报告可追溯，新报告能说明使用了哪些版本。

## R4 · P2 · 内容哈希唯一约束会漏记 JD 恢复到旧内容的变化

**证据：** 架构 §4.2（L112）要求 `(source_key, source_job_id, content_hash)` 唯一，§4.3（L125）又要求内容不同就追加版本。现有 [store.py](../src/interview_copilot/jobs/store.py) L35、L125–130 使用相同唯一约束及 `INSERT OR IGNORE`。

**已复现：** 用 SQLite `:memory:` 顺序写入同一岗位 A → B → A，三次返回 `changed=True`，当前内容正确恢复为 A，但 `versions()` 只返回 A、B，第三次变化及其发生时间丢失。

**修订要求：** 区分内容去重与变更历史。可以每次相对当前内容发生变化就追加修订，也可以复用去重内容并另存变化事件；不能只靠内容哈希表示完整时间线。相邻相同内容抓取仍应幂等。

**复审验收：** A → A 不增加内容修订，A → B → A 保留三次变化所处的顺序及时间。现有缺陷尚未修复，不以原测试全绿抵销本条。

## R5 · P2 · 接入契约仍以“能搜索的岗位来源”为中心，遗漏独立能力入口

**证据：** 架构 §5.1（L134–143）从 `search()` 开始，并将搜索未验证渲染为该来源暂不可用；§6 只有搜索、详情、投递、反馈四类。被架构采纳的 [sources/base.py](../src/interview_copilot/sources/base.py) L32–42 强制实现搜索与详情。VISION §4.2（L232–234）要求发现、投递、反馈分开，邮箱可以仅提供反馈，提交与结果查询也分别声明；BOSS 单岗链接是已明确的独立路径。

**触发场景：** BOSS 搜索未验证但详情读取已验证时，用户粘贴链接仍应可进入详情获取；邮箱反馈接入不应实现虚假的岗位搜索方法；能够填写或提交表单也不等于能够查询提交结果。

**修订要求：** 按实际能力组织端口/协议及注册方式，允许搜索、链接详情、材料准备、提交、结果核验、反馈各自接入。补齐链接/文本导入到统一岗位记录的路径，并以同一机会关联不同发现来源、投递渠道和反馈入口。接口可以在同一适配器实现，无需拆成多个部署服务。

同时把证据阶段、验证范围、产品接入状态与账号连接状态分开。§6 的“在项目环境取得证据 → 界面可用”不足以区分一个脚本样本与已接入产品；声明为已验证也不能忽略账号授权失效。

**复审验收：** 仅详情的来源、仅反馈的入口、提交已验证但回执查询未验证的渠道，都能表达和执行各自范围，不修改机会/面试核心逻辑，也不冒报其他能力可用。

## R6 · P2 · 缺少本地运行与后台任务设计

**证据：** 架构 §5.3（L163–165）承诺本机调度及转写恢复；§8 只明确浏览器独立进程；AQ1/AQ7 留待验证，但全篇没有 UI、录音、转写 worker、调度器和存储的运行关系，也没有任务持久化与重启恢复约定。

**触发场景：** 关闭主窗口后转写是否继续，机器休眠后错过的提醒如何展示，录音中断后已落盘片段如何恢复，耗时模型调用是否阻塞界面，均无法从现有设计决定。SQLite 保存了业务记录，不等于自动保存任务进度或音频文件。

**修订要求：** 给出首版进程/任务图，明确生命周期、任务状态、取消与恢复、音频落盘策略、数据库与文件写入的协调方式、提醒补偿及离线边界。可以是本地后台进程与持久化任务记录，不要求云服务或消息中间件。反馈读取还需定义每渠道同步游标、重复事件键和最近成功同步时间。

**复审验收：** 主窗口关闭、后台退出、进程崩溃、休眠恢复、网络失败分别说明哪些动作继续、暂停、补偿或需用户处理，并有对应隔离验证计划。UI 框架可待采集实测后选定，运行契约需先确定。

## R7 · P2 · 可同步的改进清单没有独立的数据归属

**证据：** 架构 §3（L91）及 §5.3（L168）提到改进项，但 §4.2 只给出不可同步的 `review_reports`，没有改进清单实体、引用或完成状态。VISION §6（L370）及 D5（L446）明确：报告全文只在本机，改进清单及进度未来同步。

**触发场景：** 如果把改进项仅写入报告正文，未来只能重新解析报告提取清单，或连同不应同步的报告一起传输。重新生成报告也可能覆盖用户已经完成、修改或标记有用的事项。

**修订要求：** 明确独立的改进项记录，包含稳定标识、报告来源引用、优先级、用户修订及进度；重算报告与用户进度分别处理。首版仍只存本机，记录未来同步时允许的字段，避免嵌入转写全文或报告全文。

**复审验收：** 新报告不会清空旧改进项的用户进度；关闭报告后仍能管理改进清单；同步边界能独立于报告表达。

## 一并修正的表述与边界

- **依赖图与文字不一致：** §2 图形画成 Domain → Sources → Storage，文字却禁止 Domain 知道具体来源；应用服务允许依赖的列表也未说明来源接口。应分别标注数据流与代码依赖，并明确应用服务如何调用来源、由谁统一落库。`gateway` “唯一外部出口”也需说明招聘 HTTP 属于哪条路径，不能让两个层各自声称独占。
- **文字外发边界：** A7“转写全文不出本机”与同段“文字可外发”、§5.3 存在歧义。按 VISION D4a 写成：音频不上传；转写不做云端存储/同步；分析所需文字按配置发送外部模型。不把用户已经澄清的决定重新打开。
- **离线边界：** A1“除模型分析与抓取外，其余功能可用”漏掉投递和反馈同步的联网要求，应按本地查看/编辑、后台处理、外部执行分别说明。
- **用户资料输入：** `profile/` 不能只靠一行模块说明交接。补出导入/编辑 → 提取草稿 → 用户确认事实 → 材料版本的流程，以及 AI 派生内容与用户确认事实的区分。这承接 D9，不新增产品目标。
- **技术待定不是交给用户猜：** 由开发依据录音、提醒、渠道登录实验推荐界面形态和依赖，用户只需提供真实设备与使用约束。无需为了这轮架构审查预先选择模型厂商或新增基础设施。
