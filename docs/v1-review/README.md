## 1. 目标与边界

完整目标仍是：已有资料 → 找岗与选岗 → 手动投递 → 反馈与面试 → 面试内容 → 复盘与改进 → 下一轮。保留 [VISION v0.12](../../VISION.md) 的首版范围；本次提出新的分块和推进顺序，不删除原有承诺、不重开已确认的自动投递/本地转写边界。

每块都包含使用结果、功能、数据、交互、异常、验收。页面、接口、存储在同一块交付；数据结构是业务块的内部支撑，不另建一个必须全部开发完才可用的数据库阶段。

已有资料、已有申请、已有面试均可直接进入对应步骤。开发顺序不成为用户必须完成前一步的限制。

文字等价路径：M1 和 M2 为 M3 提供材料与岗位；M3→M4→M5→M6；M6 的改进回到 M1/M4。允许直接补录 M3/M4；M6 可以使用 M5 的手工回忆，无需强制有音频。

建议审阅顺序：总览及[共享数据边界](data-flows.md) → M1 → M2 → M3 → M4 → M5 → M6。G 的对应条款随每块一起审，最后核对完整发布条件。

每块依次完成以下状态，不能把讨论或上一轮代码 review 当作本轮批准：

1. **待审**：负责人给出具体使用场景、页面状态、数据关系和验收例子。
2. **需求/设计通过**：记录用户确认的文档版本、范围及消息依据；待定事项必须明确是否阻塞本块。
3. **实现**：在功能工作区先写目标行为测试，证明旧实现因该行为失败，再改实现；已有能力按证据复用。
4. **技术与使用验收**：完整测试、跨个体代码审查，以及交付版本上的真实操作；界面先提供可见草案，按审定方向实现。
5. **本块可用**：记录代码版本、运行版本、隔离数据目录及用户可用结果；推进下一块。局部放行不等于首版完成。

审阅关注三个问题：这块是否解决你的实际任务；是否重复索取已有信息；完成后是否能接下一块。技术字段和测试安排由负责人负责解释与落实，不要求用户逐列设计数据库。
